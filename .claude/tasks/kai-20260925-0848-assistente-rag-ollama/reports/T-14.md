## Desvios do plano
- O `FileInterceptor` do Nest traduz o `LIMIT_FILE_SIZE` em `PayloadTooLargeException` (HttpException, sem `code`) antes do filtro global, então o ramo `MulterError` do `all-exceptions.filter.ts` nunca é atingido. Para cumprir o 413 `ATTACHMENT_TOO_LARGE` sem editar o filtro (fora do escopo), criei o `AttachmentTooLargeInterceptor` dentro de `document.controller.ts`, aplicado só no `POST /documents` e por fora do `FileInterceptor`.
- `DeleteDocumentUseCase` chama `findById` antes: documento inexistente responde 404 sem tocar no vector store. Se `repository.delete` devolver `false` (corrida), responde 404 também. A ordem `deleteByDocument` → `delete` segue o plano.
- `ListDocumentsUseCase` usa os defaults `page=1` e `limit=20` (os mesmos do `PaginationQueryDto`).
- `UploadDocumentDto` virou um DTO só para o Swagger (`file` binary via `@ApiBody`). O controller não faz binding de `@Body`, então o `forbidNonWhitelisted` não interfere no multipart.
- Upload sem o campo `file` → 400 `Campo file é obrigatório.` (não estava especificado).
- `DocumentVectorsGateway` injeta `VECTOR_STORE_CLIENT` a partir de `documents/infra/gateways/`. O comentário do `VectorStoreClient` só cita `embedding`/`retrieval` como consumidores.

## Pendências
- `multer` (de onde vem o `memoryStorage`) é dependência transitiva de `@nestjs/platform-express`, não direta no `package.json`. Funciona (hoisted e com `@types/multer`), mas vale declarar a dependência numa task que possa mexer no `package.json`.
- O comentário do `all-exceptions.filter.ts` (ramo `MulterError`/`AttachmentTooLargeInterceptor`) está impreciso. Fica para a revisão final ou para a T-17 (fora do meu escopo).
- Contrato alterado para o frontend e para o smoke da T-18: o `POST /documents` JSON antigo deixou de existir (registrado no board).
